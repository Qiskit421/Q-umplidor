# ADR-0003: Mecanismo de persistencia de trabajos

## Estado
Resuelto por [ADR-0005](ADR-0005.md) (Avance 02): JSON con escritura atómica. Se conserva como historial de la propuesta.

## Contexto y problema
El sistema deberá conservar metadatos y resultados mínimos después de reiniciar el servicio (RF-12), recuperar el historial al arrancar y marcar correctamente los trabajos interrumpidos (RF-13, RNF-10), evitar dejar archivos a medio escribir (RNF-11, RNF-28), y soportar al menos 500 registros sin pérdida de metadatos (RNF-06).

## Alternativas consideradas
### Opción A — Archivos planos (JSON / JSON Lines)
Cada trabajo se guarda como archivo o línea independiente, escribiendo con el patrón 'temporal + rename atómico'.
* **Ventaja:** Sin dependencias externas, fácil de inspeccionar manualmente y de usar como evidencia reproducible.
* **Riesgo:** Hay que implementar a mano la atomicidad (RNF-11/28) y las consultas por filtro (RF-09) escalan peor a partir de cientos de registros.

### Opción B — SQLite
Una sola base de datos embebida con una tabla `jobs` (id, estado, tiempos, código de salida, rutas de stdout/stderr).
* **Ventaja:** Atomicidad y consistencia dadas por el motor; consultas y filtros (RF-09) triviales con SQL; buen soporte para los ≥500 registros de RNF-06 y el límite de 1s de RNF-05.
* **Riesgo:** Una dependencia más que documentar y fijar versión; el equipo debe manejar bien transacciones para no violar RNF-27/28.

### Opción C — Persistencia en memoria + snapshot periódico (descartada)
El estado vive en memoria y se vuelca al disco cada cierto intervalo o al recibir señal de apagado.
Descartada preliminarmente: Una falla no controlada (no un apagado limpio) perdería trabajos completados entre snapshots, en conflicto directo con RF-12 y RNF-30/31.

## Decisión
Pendiente. Tendencia inicial hacia la Opción B (SQLite) por dar atomicidad 'gratis' para RNF-11/28 y facilitar las consultas de RF-08/09 bajo el límite de RNF-05, a confirmar con un prototipo simple de escritura y lectura antes del Hito 2.

## Consecuencias
* **Positivas:** Menos código propio para garantizar atomicidad; consultas y filtros más simples.
* **Negativas / riesgos:** Dependencia adicional a declarar y fijar versión; necesidad de manejar bien conexiones concurrentes desde el hilo supervisor definido en ADR-0002.

## Requisitos afectados
RF-08, RF-09, RF-12, RF-13, RNF-05, RNF-06, RNF-10, RNF-11, RNF-28, RNF-31.

## Evidencia / prototipo
Pendiente: Prueba de reinicio del servicio con trabajos en QUEUED/RUNNING antes del corte, verificando que ninguno se reporte como RUNNING de forma falsa (vinculada a TC-007).
